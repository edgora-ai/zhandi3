# 开发与排障笔记

本文记录项目开发中已经遇到的问题、确认过的根因和可复用的工程方法。后续修改输入、暂停、渲染、程序化网格、音频或大规模场景前，应先阅读本文；解决新问题后，也应按“症状、证据、根因、修复、回归测试”的格式继续补充。

## 1. 工程原则

### 1.1 一切由代码生成

- 场景文件保持简单，建筑、地形、植被、载具、特效和材质由 GDScript 创建。
- 位图贴图通过程序生成，音效通过 `tools/gen_sfx.py` 生成，不依赖外部素材站。
- 重复结构优先提取工厂函数，共享 Mesh、Material、Texture 和 MultiMesh，避免大量重复资源。

这样做有利于版本审查、固定随机种子复现和自动化测试，但也意味着节点生命周期、碰撞层和资源复用必须显式管理。

### 1.2 新类先刷新类缓存

脚本使用 `class_name` 注册全局类。新增类后，引用它的其他脚本可能在类缓存更新前报错，因此第一步必须执行：

```bash
tools/Godot.app/Contents/MacOS/Godot --headless --path . --import
```

不要把“缓存尚未刷新”误判为代码依赖错误。

### 1.3 GDScript 类型要保守

字典取值、`get_nodes_in_group()`、元数据和动态属性通常返回 Variant，不能依赖 `:=` 推断。使用显式类型，例如：

```gdscript
var target: Node3D = value
var position_value: Vector3 = data["position"]
var members: Array = get_tree().get_nodes_in_group("combatant")
```

显式类型既能避免编译错误，也能让物理、AI 和程序化生成代码更容易审查。

## 2. 输入系统的历史问题

### 2.1 持枪后不能转向或开火

症状：徒手状态正常，显示武器和准星后鼠标转向、开火失效。

根因：HUD 中位于屏幕中心的 Control 默认使用 `MOUSE_FILTER_STOP`，捕获模式下鼠标事件仍会被它吞掉，无法到达玩家的 `_unhandled_input()`。

修复：HUD 根节点和所有动态创建的子控件统一使用 `Control.MOUSE_FILTER_IGNORE`。新增 HUD 控件时必须继续遵守这一规则，不能只设置根节点，因为子控件仍可能独立拦截事件。

经验：输入故障要按“系统是否收到事件 → GUI 是否消费事件 → 玩家状态是否允许处理 → 武器是否处于冷却/换弹”逐层排查，不要直接怀疑武器逻辑。

### 2.2 鼠标捕获丢失造成“假死”

症状：画面仍在更新，但玩家不能转向或射击。

根因：Esc、应用切换或系统手势可能把鼠标从 `MOUSE_MODE_CAPTURED` 切回可见模式。

修复：鼠标未捕获时，左键只负责重新捕获，不触发本次射击；Esc 可显式释放或重新捕获。

经验：FPS 必须把“游戏暂停”和“鼠标未捕获”视为两个不同状态。画面是否更新、角色是否移动、鼠标是否可见，是区分它们的关键证据。

## 3. “画面停住但声音继续”复盘

### 3.1 症状与错误方向

试玩时游戏运行一段时间后画面和操作停止，但背景音乐仍在播放。该现象很像主线程死循环、GPU 卡死或内存泄漏，不能仅凭声音继续就下结论。

排查中使用了以下证据：

- 无头比赛心跳持续输出，节点、对象、资源和静态内存没有持续增长。
- 窗口化 3600 帧测试能够正常结束，说明渲染和游戏主循环没有稳定复现的死循环。
- 标准 Finder/Godot 切换会触发焦点暂停和恢复。
- 音频播放线程不会因为 SceneTree 暂停而自动停止，所以“还有声音”不能证明游戏逻辑仍在运行。

### 3.2 根因

窗口失焦时游戏会设置 `get_tree().paused = true`。旧实现只依赖一次 `NOTIFICATION_WM_WINDOW_FOCUS_IN` 来解除暂停；macOS 偶发漏发或错序发送恢复通知时，普通节点已经因 SceneTree 暂停而停止处理，无法自救，而音频线程继续播放，于是表现为永久卡死。

### 3.3 修复设计

- 同时处理窗口级和应用级焦点进入/离开通知。
- 用 `_focus_pause_owned` 记录暂停所有权，只解除本模块发起的暂停，不能覆盖未来菜单等系统的暂停。
- 创建 `PROCESS_MODE_ALWAYS` 的独立 Timer；即使 SceneTree 已暂停，它仍能轮询 `DisplayServer.window_is_focused()` 并恢复。
- 失焦时同步设置所有 AudioStreamPlayer 的 `stream_paused`，恢复时继续播放，让声音状态与游戏状态一致。
- 保留日志：`[focus] paused after focus loss` 和 `[focus] resumed`，方便判断卡住时是否停在焦点链路。

### 3.4 回归测试

使用以下命令模拟“已经暂停但没有收到恢复通知”，确认 ALWAYS Timer 可以自动解锁：

```bash
tools/Godot.app/Contents/MacOS/Godot --headless --path . --quit-after 120 -- --noworld --ground --focusrecoverytest
```

期望日志顺序：

```text
[focustest] simulating a lost focus-in notification
[focus] paused after focus loss
[focustest] ALWAYS timer ticked while the scene tree was paused
[focus] resumed
```

经验：任何会暂停自身执行环境的模块，都必须提供在该环境之外运行的恢复路径。

### 3.5 相同症状的第二个根因：延迟删除导致无限循环

四季改动后再次出现“画面停止、声音仍在播放”，但这次活动监视器显示 Godot 占用约 88GB 内存。现场证据与失焦暂停完全不同：

- 固定种子战局在第 6 条季节/占点/击杀播报附近停止心跳，主线程接近 100% CPU。
- macOS `sample` 显示进程 physical footprint 已达 42.4GB，主线程持续进入 `malloc`；终止测试时记录到 67.4GB 峰值 footprint。
- 引擎内 `Performance.MEMORY_STATIC` 仍显示约 180MB，说明只看 Godot 静态内存监控会漏掉这类主线程分配风暴。

根因是 HUD 用下面的逻辑限制播报数量：

```gdscript
while container.get_child_count() > 5:
    container.get_child(0).queue_free()
```

`queue_free()` 只把节点标记为帧末删除，当前循环里的 `get_child_count()` 不会下降。因此第 6 条播报加入后条件永久为真，同一个节点被反复排队删除，CPU 和内存会在单帧内失控。

正确做法是先让容器状态立即收敛，再延迟释放：

```gdscript
while container.get_child_count() > MAX_ITEMS:
    var oldest := container.get_child(0)
    container.remove_child(oldest)
    oldest.queue_free()
```

专用回归测试会一次加入 12 条播报，并确认最终只保留 5 条：

```bash
tools/Godot.app/Contents/MacOS/Godot --headless --path . --quit-after 30 -- --noworld --feedtest
```

期望日志：`[feedtest] items=5 expected=5`。经验：不要在同一循环中依赖任何延迟执行 API 改变循环条件；`queue_free()`、`call_deferred()` 和 `set_deferred()` 都应按这个原则审查。

### 3.6 macOS 崩溃报告可能发生在游戏尚未启动之前

用户提供的一份 `EXC_BAD_ACCESS / SIGABRT` 报告中，Godot 从启动到退出只有约 1.3 秒，工作线程都停在条件变量等待，主线程栈只有未符号化的 Godot 引擎地址，没有任何项目启动日志。这与“玩了一段时间后内存达到 88GB”的 HUD 无限循环不是同一次故障。

本轮自动化复测中，在短时间并行启动多个 Godot 进程后复现了相同形态的引擎启动崩溃，崩溃前先输出：

```text
Failed to open 'user://logs/godot<timestamp>.log'
handle_crash: Program crashed with signal 11
```

证据更符合 Godot 4.7.1 macOS 版本在默认 `user://logs` 轮转或并发写入时的引擎侧竞态，而不是游戏场景运行后的资源泄漏。验证时采用以下规避方式：

- 同一项目的 Godot 长测串行执行，不要让多个进程共用默认用户日志；
- 每个自动化进程传入唯一日志，例如 `--log-file /tmp/zhandi3-wild-long.log`；
- 报告崩溃时先核对启动时长和 `[boot]` 是否出现。没有 `[boot]` 的 1 秒启动崩溃不能用来判断玩法脚本；
- 仍需用节点数、对象数、RSS/footprint 和固定帧心跳独立验证游戏运行期内存。

经验：系统崩溃报告、游戏卡死和测试工具自身失败可能同时存在，必须先按 PID、时间、启动参数和最后一条项目日志把事件分开。

## 4. 程序化渲染与碰撞

### 4.1 Godot 4 API 和 shader 易错点

- 描边材质使用 `grow`，不是 `grow_enabled`。
- shader 中实例变换矩阵使用 `MODEL_MATRIX`，不是 `INSTANCE_TRANSFORM`。
- 自建网格的前向面采用顺时针绕序。绕序错误可能看起来只是剔除问题，但 trimesh 单向碰撞也会失效。
- 地形碰撞已启用 `backface_collision`，其他自建 trimesh 仍应从源头保证绕序正确。

### 4.2 大规模植被

草、花和树冠卡片使用 MultiMesh，避免为每个实例创建节点。需要注意：

- MultiMesh 减少 CPU 和节点开销，不代表 GPU 成本为零；实例数量、每实例顶点数和顶点 shader 噪声计算仍会相乘。
- 尽量共享网格、shader 材质和程序化贴图。
- 关闭不必要的阴影，透明卡片优先使用 alpha scissor；大面积 alpha blend 容易产生过度绘制。
- 无头测试不会覆盖真实渲染压力，视觉功能必须补充窗口化长时运行和截图。

### 4.3 水体和程序化贴图

水体使用解析地形高度烘焙出的单通道高度图，实现深浅水色、岸线泡沫、扩散雨环、冬季冰裂和波浪。经验是把 CPU 上稳定、可复现的地形数据一次性烘焙给 GPU，而不是每帧在脚本中查询大量采样点。

树叶、草叶和花朵贴图集中在 `TexGen` 生成。新增纹理时应复用工厂和固定种子，保证截图可复现。

### 4.4 从 Elemental-Serenity 迁移的方法

本轮对照了 `/Users/ahoo/Documents/kimi/Workspaces/Elemental-Serenity`。参考工程使用 Three.js、外部 GLB 和贴图，不能直接复制到本项目；真正值得迁移的是组件组织与视觉分层方法：

- 一个 SeasonManager 保存每个季节的地面、草、树、岩石、水、天空、雾和灯光配置，再通过事件统一更新消费者。
- 地面不是单一颜色，而是基础生物群落色、宏观噪声、细节噪声、岩层、湿润和积雪的组合。
- 水体拆成基础深浅水色与独立效果层：岸线环、雨滴飞溅、冰层分别由强度参数控制。
- 场景造型依赖二级轮廓：桥板之外有立柱和绳索，墙体之外有梁柱和基座，屋顶之外有屋脊、檐口和雪盖。
- 季节变化不只是换一张颜色表，还会改变天气粒子、花朵显隐、灯光色温、雾色、曝光和水面运动。

在 Godot 版本中已迁移为：

- `SeasonSystem` 统一控制春、夏、秋、冬，支持 `V` 键和 `--season` 参数。
- `ground.gdshader` 叠加多尺度斑驳、坡面岩层、湿润与朝上表面积雪。
- `water.gdshader` 在高度图深度基础上增加雨环和冬季冰裂，并在结冰时减弱顶点波浪。
- 草、阔叶树、松树、花朵、天空、雾、三灯架设和曝光使用同一季节配置。
- 花瓣、秋叶和雪使用 CPU 更新的 MultiMesh。最初使用 GPUParticles，但窗口截图快速退出时 Godot 4.7.1 会报告内部 `ParticlesShaderRD` 未释放，因此改用资源生命周期更可控的 MultiMesh。
- 房屋增加石基、木构梁柱、十字窗棂、屋脊和檐口；仓库增加压条；码头增加高立柱和分段下垂绳索；屋顶预建雪盖并按季节显隐。

### 4.5 尚未迁移的候选项

以下能力仍值得后续按优先级评估，但不能为了“看起来更多”一次性全部塞进主循环：

1. 独立昼夜系统，以及季节 × 昼夜的组合色表、月亮和夜间灯笼。
2. 雨季/雷暴作为四季之外的天气状态，包括雨线、闪电、湿地反光和环境音交叉淡入。
3. 用程序化多通道 biome mask 同时控制道路、草密度、泥土、岩石和局部水塘，而不只是当前的噪声阈值。
4. 不规则池塘/溪流的局部水片和岸边几何。目前主要仍是全局海平面，复杂内陆水系需要与地形生成同步设计。
5. 岩石顶部苔藓、积雪方向遮罩和更丰富的低多边形岩簇。
6. 营地帐篷、篝火、萤火虫、风线等氛围组件；它们应服务于地图兴趣点，而不是平均散布。
7. 地形与植被分块、距离裁剪和 LOD。在继续增加细节前，应优先建立这一性能基础。

迁移原则：吸收配置结构、几何层次和 shader 思路；不引入参考工程的外部模型或纹理；每项迁移都必须有固定种子截图和运行时成本数据。

### 4.6 旷野地图：先塑造地理叙事，再填充细节

阔野地图没有把“更高还原度”理解为增加同一种树、石头或噪声的数量。纯噪声地形容易处处有变化却处处没有名字，玩家也无法形成方向感。本轮采用“解析式命名地貌 + 低频噪声细节”的分层方法：

- 先用可计算的距离场和曲线确定初始高原、双子山裂谷、西北雪山、东北火山、中央丘陵、S 形主河和东南支流；
- 再把噪声限制在坡面起伏、岩层和地表斑驳，不允许噪声破坏河槽、道路和兴趣点落脚面；
- 神庙、驿站、遗迹、桥和火口放在地貌节点或视线轴线上，让轮廓承担导航功能；
- 建筑先做一级剪影，再补二级结构。神庙由多边主体、穹顶、环形符文、门框和冠刺组成；驿站由厚石基、开放木架、大屋顶、柜台、马槽和灯笼组成，避免“一个发光方盒就是神庙”；
- 河流不是只放一张水平水片：地形函数必须先挖出连续河槽，水 shader 再根据高度图表达深浅、波浪和岸线泡沫，桥梁与芦苇最后沿同一条解析河线布置。

经验：程序化地图的“还原感”主要来自地貌关系、尺度层级和地标布局，而不是几何数量。每个区域都应能用一句话描述、能从远处认出，并且与玩法资源或移动方式发生关系。

### 4.7 卡通开放世界风格的边界

本项目吸收的是低多边形轮廓、色块分层、空气透视、暖冷光照和可交互地标等设计方法，不复制外部游戏的模型、贴图、关卡数据或具体资产。所有地形、建筑、角色、载具和特效继续由工程代码生成。

这条边界同时有工程价值：风格由共享 `Toon` 材质、颜色配置和几何工厂控制，季节或曝光调整可以全局生效；固定随机种子可以重建相同画面；版本库也不会逐渐变成不可审查的二进制素材集合。

## 5. 玩法模块的状态边界

### 5.1 载具

玩家进入载具后，移动由 Vehicle 接管，玩家碰撞和可见性切换，摄像机改为载具摄像机；退出时必须对称恢复。输入处理要明确“驾驶中只响应哪些玩家按键”，避免玩家控制器和载具同时消费移动输入。

经验：进入/退出、装备/卸下、暂停/恢复等成对操作，应在同一模块中保持严格对称，尤其是 camera、collision_layer、collision_mask、visible 和引用关系。

### 5.2 烟雾弹与 AI

烟雾不需要创建昂贵的体积视线系统。AI 判断射线后，再计算视线线段与烟雾球的最近距离即可决定是否遮挡。

经验：先选择满足玩法需求的最小几何模型，再考虑更复杂的渲染或物理方案。视觉烟球和 AI 遮挡逻辑可以解耦，但必须共享半径等规则常量。

### 5.3 骑乘接口必须统一状态边界

马、摩托和吉普车都通过 `driver`、`mount_player()`、`dismount_player()` 以及玩家的 `vehicle` 引用形成同一种状态协议。具体速度、转向、贴地和动画由载具自身处理，玩家只负责寻找最近的可骑乘对象并发起上下骑乘。

上下骑乘必须对称恢复以下状态：玩家可见性、碰撞层、碰撞遮罩、位置、朝向、相机归属和 `vehicle/driver` 双向引用。只恢复其中一半，常见结果是下车后隐身、没有碰撞或两个控制器同时消费 WASD。

### 5.4 游泳与滑翔要控制速度，不要直接改位置

游泳使用水平目标速度、垂直输入和水面浮力共同驱动 `CharacterBody3D`：没有输入时把角色原点拉向水面下固定深度，空格上浮、C 下潜、Shift 提速。这样玩家能稳定露头，同时保留碰撞和连续速度；把 `global_position.y` 每帧硬设为水面会导致岸边抖动和穿越碰撞。

滑翔同样继续走速度积分：将水平速度朝输入方向收敛，并把最大下坠速度限制为 `-3.1m/s`。落地、入水或松开空格时显式收起斗篷。专用回归不能只检查布尔值，还要记录高度差、垂直速度和水平位移，避免“动画展开了但物理没变”的假通过。

### 5.5 生态和投射物使用有界生命周期

石块、龙焰和能量弹共用 `WildProjectile`，只把材质、速度、伤害、尺寸和寿命作为参数。每个投射物必须同时有碰撞终止和超时终止，命中后立即退出；敌人攻击冷却也必须有下限，否则长时运行时节点数会随射击次数持续增长。

动物死亡统一通过战利品系统生成兽肉，巨龙生成龙鳞。阔野回归测试依次验证投射物实际扣血、动物死亡前后 loot 数量变化，并在结束时打印总节点数和静态内存。固定 3600 帧测试中应重复观察节点数，不能只看退出时的单点值。

### 5.6 载具“能移动”不等于手感成立，滑翔不能只绑定开局空降

症状：玩家反馈马匹轮廓不像马、骑马与开车转向生硬；角色开局落地后再次从高处下降时无法展开滑翔伞；桥面过窄，驿站像只有一个顶棚。

证据与根因：

- 旧桥面宽度只有 `2.2m`，只能作为人行栈桥；驿站主体由两片斜屋面和一个方盒承担，缺少客栈、廊道、马厩与服务设施的层级。
- 马、摩托和吉普把标量速度直接投到每帧的新朝向，固定转向率同时瞬间改写移动方向，没有油门/刹车阶段、速度相关转向、横向抓地差值或可独立观察的骑乘镜头。
- 马头使用过大的深色口鼻和过长耳朵，头颈接近竖直，近景更像羊驼；四匹马又共享同一配色，进一步暴露复制感。
- 滑翔条件硬编码为 `is_dropping`。该值在第一次落地时被永久设为 `false`，所以物理限速与伞面虽然存在，后续跳崖永远无法触发。
- 滑翔伞位于第一人称相机背后，即使状态为真，玩家也很难看到展开反馈。

修复：

- 海利亚桥改为约 `44m × 7.2m` 的分段缓拱桥，加入连续碰撞、桥墩、护墙、门塔与道路接驳；驿站改为 26 米圆形客栈、环廊、住宿间、柜台、马槽、拴马栏、货箱、灯笼和多层帐篷顶。
- 三类骑乘物统一使用渐进目标速度、独立刹车/滑行衰减、平滑转向、随速度降低的转向率，以及“期望朝向速度—当前惯性速度”之间的抓地收敛；模型单独跟随坡面和转向压倾，相机可用鼠标环绕并在行驶中柔和回正。
- 马匹重做为前伸的收分长脸、短耳、斜颈、加长躯干、分段四肢与连续尾巴，并提供四组毛色。
- 滑翔部署改用“开局空降，或离地超过 `2.35m` 且持续下降”的条件；普通跳跃不会误开，落地后的悬崖跳跃可以再次展开。伞面移到镜头前上方，加入开伞缩放、伞绳与握杆，展开时收起枪模。

回归：使用固定 60 FPS 的 `--wildtest`，日志必须同时出现 `cliff_glide active=true visual=true`、垂直速度不低于 `-3.10m/s`、马匹与摩托产生有效位移，以及吉普产生可观测的位移、转角和制动降速。视觉截图分别检查马匹侧面、骑乘后视角、驿站、大桥和第一人称伞面，不能只凭节点可见性判断。

### 5.7 第二轮“像不像”迭代：轮廓交给专用网格，地标承担远景，手感对齐参照物

第一轮修复后试玩仍反馈“不行”，逐项复查得到第二轮根因：

- 马头用胶囊+圆锥近似，任何角度都缺一段“笔直的长脸”。改用 8 顶点手工楔形棱柱（后脑宽、鼻梁窄且下沉），三角形绕序按项目约定手工验证（前向面顺时针，法线取 `-cross(a,b)`）；楔形脸 + 短耳 + 立式鬃毛脊冠后，侧面剪影稳定读作马。
- 地图色阶整体偏暗，季节色调又把 wild 地图压暗 16%：深草 `(0.17,0.37,0.075)` 与 `(0.84,0.90,0.79)` 的季节乘数叠乘后远低于参照的高饱和绿。提亮到 `(0.24,0.46,0.10)`/`(0.57,0.75,0.21)` 并把季节乘数改为 `(0.97,1.00,0.90)`。
- 远景缺少“一眼认出”的天际线地标：在北部丘陵新增海拉鲁城堡（白色主堡、蓝色金字塔顶、中央尖塔、四座角塔、环形城墙），并在地形函数中为城堡单独 `_flatten_disc` 出 30m 高地；云从 14 朵小云改为 22 朵更大更扁的招牌云。
- 滑翔伞“松开摇杆就悬停垂直下落”与参照物不符：改为始终向前飘行（前向 0.72 倍基础速度），W 俯冲（1.18 倍速度、1.30 倍下降）、S 减速缓降（0.45/0.80 倍），回归日志仍要求无输入时 `vy=-3.10`。

经验：卡通开放世界的“像”来自三件事的叠加——近距离物体的一级轮廓（楔形脸）、中距离建筑的功能层级（驿站环廊）、远距离天际线地标（城堡、雪山、火山锥）。任何一层缺失都会让整张地图退回“随机绿地”。手感类反馈要对齐参照物的默认行为（马始终向前、伞始终前飘），而不是只调参数数值。

### 5.8 第三轮：道路要画进地形，楼梯是斜坡不是台阶，骑乘要镜头相对

症状：试玩反馈“没有楼梯、没有道路、骑马和摩托手感很差、总体细节不多”。

证据与根因：

- 旧“道路”是 0.075m 厚的散置瓦片，玩家视高几乎看不见；真正的路必须成为地表的一部分。
- 高塔、城堡、神庙、桥头都没有可行走的上行通道；最初补的垂直台阶在回归中暴露：玩家走过去 `climbed=-0.30`，一步都没上去。
- 根因：Godot `CharacterBody3D.floor_snap_length` 只把身体向下吸附保持贴地，**不会把胶囊体抬上垂直台阶**；垂直踏面在物理上是矮墙。
- 马和摩托的手感根因是参照系错误：W 让载具沿“自身朝向”走，而玩家的空间参照是镜头朝向，两者分离造成“想往哪走对不上”。

修复：

- 道路改为解析线段网（`Terrain.WILD_ROADS`），在 `_vertex_color` 中按点到线段距离混入土色，远看近看都是连续道路；路口加木质路标、沿途加石灯。
- 楼梯统一为 `_staircase` 构件：一条带仰角的碰撞斜坡（坡度 < `floor_max_angle`，胶囊体可靠滑上）+ 坡面上逐级摆放的纯视觉踏面。应用于测绘塔螺旋梯（约 55 段连续坡）、城堡大门、神庙会门、海利亚大桥两端引桥；回归测试要求玩家沿城堡台阶步行后高度上升约 2m。
- 马与摩托改为镜头相对操控：W/A/S/D 先在镜头偏航坐标系合成期望方向，马体以“速度越快转向越钝”的速率平滑转向该方向；站立时 A/D 原地转身。
- 细节补充：驿站围栏马场+干草垛+货车、路标、石灯、遗迹断柱、蝴蝶。

经验：一切“能走”的构造都必须有自动化行走回归（ teleport + debug_move + 高度断言 ），视觉看起来像楼梯不等于物理上能走；操控手感要先确定参照系（镜头相对还是载具相对），再谈参数。

### 5.9 第四轮：攀爬/砍树/战斗反馈——机制比装饰更难假装

症状：试玩反馈“不能爬树砍树爬塔、怪物好像打不死、地形平庸、树形单一、打斗乐趣少”。

证据与根因：

- 小怪/巨龙/飞行器的 `take_damage` 链路其实完整，但命中零反馈（无飘字、无闪光、无播报），死亡瞬间 `queue_free` 消失，玩家自然认为“打不死”。
- 树干碰撞只是普通 StaticBody，武器命中只能打出火花，没有砍伐语义；树冠是全局 MultiMesh，单树隐藏需要记录每棵树的实例索引区间。
- 攀爬在 BotW 式地图是移动系统的一半，只做了滑翔伞等于只有下降没有上升。

修复：

- `DamageNumber`（Label3D 广告牌飘字）统一给所有可伤害目标提供命中数字；小怪加受击缩放闪光、死亡倒地动画与击杀播报，巨龙血量 420→260、小怪 82→60。
- `ChoppableTree` 组件替换树干碰撞体：受击两次倒伏（绕基座轴向旋转，倒向远离攻击者），Props 用记录的 MultiMesh 索引区间把该树树冠实例缩放至 0，倒伏完成后留木桩并生成“木材”战利品（背包第四种材料）。
- 攀爬：胸前射线命中 `normal.y < 0.45` 的陡面且推 W 即进入攀爬态；攀爬中 W/S 上下、A/D 沿墙横移、Space 蹬离、胸口越过顶沿自动翻越。树干、塔身、悬崖、石柱同一生效；塔顶平台补了碰撞作为落点。
- 树形：8% 巨树（粗双段干+根膨+五簇冠）、阔叶树随机侧枝与簇位置抖动。
- 单实例锁对无头与 `--screenshot` 自动化放行，避免用户试玩窗口挡住回归测试。

回归：`--wildtest` 新增 monster dead/loot_delta、tree_chop falling、tree_wood loot_delta、tower_climb rose 断言。

经验：战斗“手感”大头是反馈而非数值——先保证每次命中有数字、有闪光、有结果，再谈平衡。MultiMesh 批量渲染与个体交互（砍倒单棵树）可以共存：记录每棵树的实例索引区间，交互时把区间内置零，避免重建 MultiMesh 或退回逐节点渲染。

### 5.10 第五轮：滩涂、补给、NPC 与“不会自己上台阶”

症状：试玩反馈“怪物都在河里、弹药枪支补给太少、只有自己一个人、河岸太陡峭爬不上来、楼梯必须蹦上去”。

证据与根因：

- 怪物/野兽移动不做水体检查，追击玩家时径直走进河床沉底；河岸过渡带只有 6m 宽（7m 高差 → 45°+ 陡坡）。
- 阔野地图从未生成分布式补给（`_spawn_loot_field` 仅战场图），全图只有落点一把步枪；也没有友好 NPC。
- 自动上台阶功能连续两次回归失败：第一次用 `move_and_slide()` 之后的残速当“预期速度”（被挡时两者都接近 0）；改成速度阈值后又踩中**加速度模型的贴墙稳态**——ACCEL=30、60FPS 下贴墙每帧速度恰好 0.5m/s，阈值 0.6 永远不触发。
- 最终可靠判据是“有前进输入且 `get_real_velocity()` 几乎为零”，完全不依赖速度阈值。回归用探针日志（`--stepdebug`）定位，不要凭猜。
- 另一个时序 bug：补给在 `_spawn_campfires()` 之前生成，营地弹药依赖的 `_camp_positions` 还是空数组，静默丢失——涉及生成顺序的依赖必须把消费方放在产出方之后，并用数量断言（`wild_loot ammo=9`）兜底。
- `StandardMaterial3D` 没有 `darkened`（那是 `Color` 的方法）：模型构建中途报错会让后续成员保持 null，错误刷屏会淹没真实问题，第一行报错才是根因。

修复：河岸过渡带放宽到 20m（河床→沙滩→草坡）；怪物与野兽加避水检查；地标/营地/塔顶分布武器、弹药、医疗包、护甲；四位可交谈 NPC；玩家增加通用 step-up（0.68m 以内台基自动迈上）。回归：`stable_step end_y` 恰好等于石基顶面高度。

### 5.11 第六轮：野图大逃杀、树木加高、模型去抽象化

- 野图最初 `total_combatants=1`，用户期待的是“一起吃鸡的人”。Bot 对毒圈是非激活安全的（`zone.active=false` 时只搜刮/游走/交战），直接复用到野图：8 名 AI 战士分区空降，野图补给（武器/弹药）同时服务玩家与 bot，击杀全部对手同样触发胜利结算。回归观察点：`--sim` 中 `alive=9`，`wild_loot weapons` 会随 bot 搜刮减少。
- 树木“低矮到不值得爬”：阔叶树干 1.5m→2.6m（全树 4~5.5m）、松树 1.9m→3.2m（5~6.5m）、巨树到 9m，树干碰撞同步加高，爬树才有上升感。树线从 18m 抬到 26m，初始高原也有树。
- 模型“抽象”通常是缺中频结构：马补了肩胛/后躯肌群、胸口和蹄冠（四肢像从身体里长出来）；摩托补油箱、座垫、发动机散热片、挡泥板、头灯、握把。低成本部件叠加比调比例更见效。

### 5.12 第七轮：人物“效果差”的三个根因与修法

症状：试玩反馈人物角色的长相和动作与参照差距大，“不一定一模一样，而是效果太差”。

复查发现 bot 装备件（背心/背包/头盔）其实不少，真正缺的是：

1. 四肢是刚性单杆：没有肘/膝二级枢轴，走路像木棍摆钟。修法：肩/肘、髋/膝两级枢轴，小腿在前迈时弯曲、肘部保持微弯，成本只是多 4 个 Node3D。
2. 身体没有起伏：没有步频两倍的垂直 bob、没有速度前倾、站立时没有呼吸，角色像滑动的雕像。修法：`_visual` 根节点统一做 bob/lean/breath，所有部件挂在下面。
3. 没有脸：黑点眼睛在 5m 外就是空白。修法：眼白球 + 瞳孔球 + 眉条三件套，头部独立枢轴，平时偶尔环顾、NPC 靠近时注视玩家——“被注视”是角色活过来的最便宜信号。

经验：卡通角色的“效果”= 比例对（头身比、肩宽）+ 关节分段 + 身体起伏 + 一张能读的脸，四者缺一会立刻退回“抽象”。参考原作的正确姿势是提炼这些原则，而不是研究对方文件格式。

### 5.13 第八轮：把研究成果落成系统——警觉态、马匹自主性、NPC 反应、使用痕迹

本轮把“为什么旷野之息好”的分析逐条变成机制：

- 动物警觉中间态：发现玩家先定格注视（头顶 `!`）0.9~1.4s 再决定进攻/逃跑，狼加群体规则（18m 内有同伴才围攻，孤狼只警戒）。“被注意到”是动物活起来的核心信号，成本只是一段冻结计时器。
- 马匹自主性三件套：松手骑行时自动贴合道路中线（沿 `WILD_ROADS` 最近线段方向缓转）；步态分级（慢步 5Hz / 快步 8Hz / 疾驰 11Hz，频率随档位跳变，头部随步态点头）；无人骑乘时周期性低头吃草。驯服：首次骑乘 45% 概率尥蹶子甩人，安抚一次后永久温顺。
- NPC 反应：附近开枪或怪物靠近时抱头蹲下 2.6s（武器记录 `last_shot_msec` 供 NPC 轮询）；新增行商沿道路在驿站与大桥间往返巡逻。
- 建筑使用痕迹：每个火堆配三脚架炊锅、废墟柱面爬藤蔓、驿站门口补一段踩秃路（`WILD_ROADS` 末段）。

经验：每个机制都要回答“它让玩家觉得 X 是活的吗”。警觉 pose、吃草、抱头、行商这些都不是玩法闭环，但它们是“世界在运转”的证据，这正是前两轮反馈里“差距大”的真正来源。

### 5.14 第九轮：闭环系统——烹饪、种子、口哨

- 篝火烹饪：火堆旁使用生兽肉/蘑菇转化为烤兽肉/烤蘑菇（回复更强）。判定用 `_camp_positions` 半径查询，背包项从 4 种扩到 6 种，`_backpack_entry_count` 与索引数组必须同步改（漏一个就是越界）。
- 呀哈哈式种子：10 颗金色自发光种子藏在峰顶/遗迹/雪线/火山口等“专门走过去”的位置，拾取护甲 +5 并播报第几颗。稀有度光柱本身就是最便宜的“勾引探索”装置。
- 口哨召马：H 键呼唤 45m 内最近的空闲马小跑过来（`whistle_call` 设定目标点，无人骑乘时持续走向玩家，4m 内停下）。

经验：系统复刻的性价比排序——先把“猎→烤→吃”“藏→找→奖”“吹→来→骑”这类三拍闭环做出来，再谈数值深度；每个闭环都要配一条自动化断言（`cooking roast_meat=1`、`seeds=10`）。

### 5.15 第十轮：神庙试炼与成长线

- 两座神庙各有一个“限时射符文”试炼：靠近自动开启，15 秒内射中 4 个悬浮符文环，全部点亮奖励精灵宝珠（生命上限 +10），超时自动重置可反复挑战。符文命中沿用武器 hitscan 链路（`take_damage` 接口），HUD 进度条复用占点 UI（`set_capture`），没有引入任何新 UI 框架。
- 生命上限从常量改 `max_hp` 变量：所有 `minf(MAX_HP, ...)` 钳制点必须同步替换（玩家 4 处、野世界火堆回血 1 处），漏改一处就是“上限加了但加不上去”的静默 bug。
- 回归断言：`shrine_trial completed=true orb=true max_hp 100->110`。

经验：成长线的关键是“奖励反哺移动与生存”（生命上限、护甲），而不是数值膨胀；试炼谜题先用现成动词（射击）做，别急着发明新交互。

### 5.16 第十一轮：昼夜循环

- `DayNight` 用单参数 t∈[0,1) 驱动全部氛围：太阳高度角 `sin(t·TAU)`、天空顶/地平线色三段（日/黄昏/夜）、雾色与密度、环境光能量、三灯能量。一天 6 分钟，T 键可推进 1 小时，`--night` 调试参数直接入夜。
- 系统联动：狼在夜晚扩大攻击半径（孤狼也会主动）；HUD 世界状态行显示清晨/正午/黄昏/夜晚；灯笼与火堆的 OmniLight 不改参数，靠环境光下降自然成为视觉主角。
- 回归断言：`daynight phase=夜晚 night=true sun_energy 1.15->0.14`。

经验：昼夜系统的正确做法是先算一条“日照权重”曲线再让所有参数插值，不要给每个属性单独写时间逻辑；黄昏是免费的高级感，专门留一段 dusk 色带而不是线性日/夜插值。

### 5.17 第十二轮：近战挥剑

- 空手状态左键 = 挥剑：0.5s 冷却，中心射线（砍树/点符文）+ 2.6m 60° 弧形范围（怪物/动物/AI 战士）双通道判定；命中 26 伤害并走统一的 `take_damage`/飘字/掉落链路。剑是程序化视模型（刃/尖/镡/柄），仅在空手且非滑翔时可见，挥动用 sin 扫掠插值 0.3s。
- 踩坑：回归第一次挥空（60→60），原因是测试用 `look_at` 导致俯仰不确定；测试姿态要显式设置偏航 + 零俯仰。实体定位测试永远不要依赖 look_at 的隐式结果。
- 回归断言：`melee monster_hp 60->34`。

### 5.18 第十三轮：血月、呀哈哈谜题、怪物营地

- 血月：午夜计数每三夜一次，天空/雾/月光整体染红，触发怪物苏醒（按原刷新点补齐，12m 内已有活口跳过）。踩坑：跨午夜检测最初只写在 `_process`，`advance()` 跳过事件——时间事件必须收敛到 `_check_midnight` 单入口。另有 `Array[Vector3]` 被赋值未类型化数组的运行时报错，成员类型放宽为 `Array`。
- 呀哈哈谜题：风车（命中爆出种子并疾转）与可疑怪石（翻倒露种子），统一 `take_damage` 走武器/近战链路，消耗一次。
- 怪物营地：帐篷、火堆、木箱、尖桩围栏（留入口）、2 守军与护甲/弹药箱，成为有攻有守有奖励的中型兴趣点。
- 回归断言：`bloodmoon active=true enemies 15->23`、`korok hit=true seeds 10->11`。

### 5.19 第十四轮：山林专项

- 第四树种白桦（白色横纹细干 + 高处疏冠），与阔叶/松/巨树形成色彩与剪影对比；树种命名统一 `Tree*` 前缀，砍树的树冠索引逻辑零改动兼容。
- 林地地面三件套：带苔倒木（横躺+年轮端口）、蘑菇“仙女环”（九菇一环+中心微光）、蕨类 MultiMesh（三片交叉叶片一丛，320 实例一次渲染）。森林从“树+草”升级为有地面叙事的林子。
- 火山口外圈 16 根玄武岩六棱柱、雪线 8 块白顶岩石，两个极端地区获得专属地标层。

经验：地区氛围的公式是“基色 + 专属地标 + 地面细节”三者齐全；单一元素（只有雪山顶色或只有熔岩）撑不起“这是另一个地区”的感觉。

### 5.20 第十五轮：精力轮

- 冲刺 9/s、攀爬静止 5/s 移动 12/s、滑翔 5/s 消耗精力；耗尽后冲刺锁速、攀爬滑落、滑翔收伞；0.45s 无消耗后 26/s 回复。消耗标记每帧清零（`_stamina_used`），比“各系统各自通知回复”可靠。
- HUD 用 16 段环形 ColorRect 做精力轮（仅在不满时显示），绿/黄/红三档；无新绘制框架。
- 食物联动：烤兽肉回满精力、烤蘑菇 +40、蘑菇 +25，烹饪闭环因此有了第二个用途。
- 踩坑：GDScript `match` 各分支是独立作用域，跨分支传递测试变量要用成员变量而不是分支内 `var`。
- 回归断言：`stamina after_climb=82 regen_to=88`。

### 5.21 第十六轮：天气与守护者

- 天气系统与季节系统分层：季节只管色调/雪/冰，`Weather` 只管 `wetness` 与 `rain_amount` 两个 shader 参数，用 `terrain.set_weather` 直达而不走季节调色板，避免互相覆盖。雨幕是跟随玩家的 420 实例 MultiMesh，雨滴在局部圆柱域内循环。
- 守护者：激光追踪（红束+眼变红）→ 2.2s 充能 → raycast 光束，给玩家明确的躲避窗口；死亡掉护甲弹药。敌人威胁等级 = 预警时间 × 伤害，先有可读预警再谈数值。
- 踩坑：GDScript 缩进级别必须连续，dedent 后不能再出现更深缩进（`Expected statement, found Indent`）；混合组里 `get_first_node_in_group` 不等于“找到那个类型”，要遍历判别。
- 回归断言：`weather rain>0 guardian dead=true loot_delta=2`。

### 5.22 第十七轮：盾牌格挡

- 空手右键举盾：正面伤害减到 1/4 并耗 10 精力（精力空则格挡失败），移动减半；举盾瞬间 0.18s 内为完美格挡，无伤并反震 12 伤害。判定用攻击者方向与面向点积（>0.25 才算“正面”）。
- 回归断言：`shield blocked=5 parry=0`。

### 5.23 第十八轮：精灵复活、第二试炼类型、NPC 作息

- 精灵复活挂在 `die()` 而不是 `take_damage()`：护甲/格挡都拦不住的致死伤害才消耗精灵，复活给 30% 生命 + 满精力，避免“复活了马上又死”的挫败链。
- 第二试炼用同一套 `ShrineTrial/ShrineRune` 骨架，`torch_style` 换视觉（石碗+火焰）和命中表现（点燃而非点亮）——谜题类型差异先做皮肤差异，规则差异少量渐进。
- NPC 作息：夜间站回落脚点俯身打盹、定时冒 Zzz；行商不受昼夜约束（巡逻优先）。

### 5.24 第十九轮：古代剑、盾滑、压力板试炼

- 近战成长线：`melee_damage` 变量化，古代剑拾取后 26→42 并换金刃材质。成长型数值永远不要写死常量。
- 盾滑的三个坑：①格挡状态被输入逻辑每帧重置（测试要 `debug_block` 钩子，且钩子要放在物理帧开头而不是鼠标捕获分支里——无头环境该分支不执行）；②陡坡（>45°）`is_on_floor` 为 false，要用“离地高度差”判定贴地；③步行衰减（0.5/帧）会吃掉弱加速，盾滑必须直接接管水平速度而不是叠加。
- 压力板试炼沿用 ShrineTrial 骨架的第三种模式（站盘 4 秒），三座神庙三种体验。

### 5.25 第二十轮：林克时间、抓鱼、石头阵

- 林克时间的正确实现是“真实时间戳 + time_scale 还原保证”：无敌帧窗口判定在 `take_damage` 入口，慢动用 `Engine.time_scale=0.22`，还原用 `Time.get_ticks_msec()`（不受 time_scale 影响），并在 `die()` 里兜底还原，绝不能只依赖流程内恢复。
- 抓鱼沿用“分组+交互扫描”的最小结构：鱼进 `fish` 组，玩家游泳时扫描 2.6m 内可用鱼，E 捕获得兽肉，60s 重生。
- 石头阵呀哈哈用“缺口坐标 + 站入保持 1s”判定，不检测石头碰撞——呀哈哈谜题的本质是“识别异常并做出行为”，而不是物理模拟。

### 5.26 第二十一轮：莫布林与烤串增益

- 莫布林的设计公式是“喂招”：0.9s 长前摇+眼部红光=明确的格挡/闪避窗口，命中 35 伤害+击退，给玩家的防御技能存在的意义。近战敌人的价值不在于难打，在于让玩家想用机制。
- 增益烹饪与占点 buff 的冲突：`_recompute_buffs` 每 0.5s 重置 `damage_mult=1.0`，会把烤串 buff 静默抹掉——临时增益必须走独立字段（`skewer_mult`），结算时再合成。
- 回归注意：同一帧块内连续的伤害测试会互相污染（闪避无敌帧、格挡状态），每项测试前显式重置相关状态。

### 5.27 第二十二轮：弓箭

- 弓不走 hitscan：按住左键蓄力（1.3/s 拉满），松开生成 `WildProjectile("arrow")`——抛物线交给共享投射物的重力项，命中判定走同一碰撞链路，箭速/伤害随蓄力插值。武器表里 `damage=0` 表示“由玩家逻辑接管”，`set_weapon` 对 bow 跳过枪械视模型。
- 投射物按 kind 分碰撞掩码：敌方投射物打玩家（1|2），玩家箭打敌人（1|4），同一份代码服务两方。
- 测试断言互相污染的新案例：烤串（肉+蘑菇）会吃掉烹饪测试的原料，测试前显式清零蘑菇库存。

### 5.28 第二十三轮：林克之家与蜥蜴战士

- 睡觉不是过场动画而是状态操作：`daynight.t` 直接拨到清晨、生命精力回满，与昼夜系统共用一条时间轴——“在家睡觉”因此成为探索节奏的一部分（夜晚危险→回家睡觉→清晨出发）。
- 蜥蜴战士是第三种敌人节奏：波克布林（中距投掷）、莫布林（慢速重击）、蜥蜴（环绕突进）——敌人矩阵按“距离×速度”铺开比按阵营铺开更出玩法。

### 5.29 第二十四轮：弹反与种子里程碑

- 弹反的判定在投射物碰撞入口：玩家举盾且面向来物（点积 < -0.3）→ 反转速度朝回发射、source 易主、弹反计数 +1，不再走伤害路径。guardian 光束是 raycast 不走投射物，天然兼容。
- 种子里程碑：每 3 颗种子精力上限 +10 并回满，种子因此同时是收集品和成长线。
- 最值钱的排障经验：测试链里“玩家在更早的环节已经死了”会让后续所有断言静默通过（死亡后 `take_damage` 直接 return、`_physics_process` 停跑、血量不变）——连续伤害测试必须先断言 `player.alive`，每个环节前显式恢复状态。这次弹反三轮假失败全是同一个根因，不是功能 bug。

### 5.30 第二十五轮：光束弹反、木筏、巨龙血条

- 光束弹反走现成的完美格挡窗口：`from is Guardian` 时反射 150 伤害——守卫 150 血正好一击自毁，和原作“完美格挡秒杀守卫”的手感一致；普通格挡仍只是减伤。
- 木筏是最小的水面载具：速度收敛 + 前方陆检停车 + 锁水面高度，F 上下共用载具协议。巨龙血条复用占点条 UI（试炼优先，110m 内显示）。
- 测试新坑：`_process` 帧内读物理帧维护的状态（blocking）会拿到上一帧的值——同步断言要自己显式置位，或把断言挪到下一帧。

### 5.31 第二十六轮：任务链与花径

- 任务系统的最小骨架：`quest_states` 四态（未接/进行/已完成/已交付）+ NPC `quest_id` 路由 + 进度基线快照（接取时记库存），HUD 用一条状态行显示进行中任务。奖励直接作用于玩家字段或掉落。
- 对话冷却要排在任务路由之后，否则“接取后立刻交付”被冷却静默吞掉——交互冷却管闲聊，不能管任务。
- 花径呀哈哈复用“目标序列+触碰推进”模式，当前目标脉冲高亮做引导，不用 UI。

### 5.32 第二十七轮：巨龙阶段与更多任务

- Boss 阶段化的最小实现：半血阈值置 `_enraged`，同一套行为改参数（转速 0.16→0.26、追击 1.6→2.6、冷却 3.4→1.8、弹数 5→8）+ 一次性播报。阶段化先改参数再谈新行为。
- 护送任务不需要 NPC 改道：复用行商既有巡逻路径，判定“到达路径索引 + 玩家在范围内”即完成——任务利用世界既有运转，而不是为任务造世界。

### 5.33 第二十八轮：血月全量苏醒与呀哈哈面具

- 血月复活的覆盖范围要和敌人类型清单对齐：新增敌人类型（莫布林/蜥蜴/守卫）时同步把刷新点记入复活名单，否则地图会随击杀永久变空。统一 `_enemy_near` 判重，避免叠加生成。
- 多源攻击增益用乘法合成而不是互相覆盖：`damage_mult = skewer_mult × charm_mult`，占点 buff 后续再乘——增益系统每加一个源都要回答“和其他源怎么叠”。

### 5.34 第二十九轮：讨伐结局与小地图

- 野图的终极目标要有结算仪式感：焚天者死亡且击杀者是玩家 → 统计面板（种子/任务/弹反/击败数），复用 `show_quest_end` 通用结算板而不是吃鸡模板。
- 小地图用“世界坐标线性映射到 164px 面板 + 静态地标点 + 玩家白点”的最小结构，不做旋转、不做缩放——导航价值 90% 来自“知道自己在哪”，而不是地图精度。

### 5.35 第三十轮：NPC 背身 bug 与人物模型重做

- 症状：玩家走近 NPC 时看见的是背影，行商沿路飞快“倒着走”，人物整体读不像人。
- 根因一（面向）：本工程角色模型的脸统一放在本地 -Z 侧，面向公式必须是 rotation.y = atan2(dir.x, dir.z) + PI（bot/moblin/horse 均如此），wild_npc 三处漏了 +PI，导致身体背对目标；头部补偿又被限在 0.6 倍，永远扭不回来。新加角色时先核对脸在哪一侧再写朝向。
- 根因二（模型）：旧 NPC 是“胶囊长袍 + 单段手臂 + 深色大鼻球”，没有腿脚、手和五官层次，深色鼻球在近景读成动物吻部。
- 修复：重做两级肩/肘手臂带手掌、髋部腿带皮靴、裙摆+腰带扣+立领、眼睛加高光点、微笑嘴、腮红、耳朵与后发/两鬓/马尾（发色随帽款）；鼻子改肤色小凸点。行走时双腿对摆，说话时右手比划 + 头部轻点（_gesture_t），独处时头部缓慢游视。
- 回归：npc_facing dot=1.00 legs=true（把玩家传到 NPC 面前跑 40 帧物理看朝向点积）。另修测试自身的随机性：Horse.enter 首骑 45% 概率尥蹶子会让骑乘回归静默跳过，测试前置 horse.bonded = true 固定结果——随机玩法分支进回归前必须先钉死随机源。

### 5.36 第三十一轮：Blender 无头管线接入骨骼动画

- 动机：代码掰关节（单枢轴 lerp/sin）做不出预备-发力-跟随的攻击三段与髋膝两级步态，这是“动作战斗”手感天花板。管线定为 tools/blender_gen/*.py（源码，提交）→ blender --background --python 无头生成 → assets/models/*.glb（可再生产物，与 gen_sfx.py/WAV 同一约定）→ Godot AnimationPlayer。不需要 Blender MCP（配完要重启会话才生效，无头 CLI 等价且更贴合“一切由代码生成”）。
- Blender 5.2 API 坑：材质 Principled 节点不能按名字找（要按 n.type == BSDF_PRINCIPLED）；Action.fcurves 已移除（动作分层化）；armature 必须先 animation_data_create() 再赋 action；多段动画用 NLA 轨道命名 + export_animation_mode='NLA_TRACKS' 导出，Godot 按轨道名播放。
- 朝向约定：Blender 中角色面向 -Y 建模，glTF 导出即 Godot 本地 -Z，与工程 atan2(dir.x, dir.z) + PI 约定一致。
- 接入模式：ResourceLoader.exists 探测 glb → 实例化 → find_child AnimationPlayer，缺失一律回退原程序化模型；换色按 Blender 材质名遍历 mesh surface 再 set_surface_override_material（村民 tunic 按 NPC coat 染色）；挂点件（三顶帽子）在 Blender 里 parent 到骨骼（parent_type='BONE'），Godot 侧按款式显隐。
- 纪律：模型与动画只改生成脚本重跑 Blender，不手改 glb；新增剪辑先在 --xxxtest 调试参数下截图核对姿态再接状态机。
- 循环地雷：Godot 导入 glTF 动画 loop_mode 默认为 0（不循环），AnimationPlayer 播完停在末帧——村民走一秒路就冻结滑行。所有 glb 角色的 _play 统一把持续状态剪辑设为 LOOP_LINEAR，一次性剪辑（windup/smash/hit/die/buck/dash/attack/death）排除在外。新角色接入时先用 --pilottest 之类打印 loop_mode 自检。
- wildtest 帧序列里禁止 await：match 按帧号逐个执行，case 内 await 会让函数返回、帧号继续推进，后续 case 的传送/改状态全部插进等待窗口互相污染（曾把 castle_stairs 打成 climbed=-21.81）。跨帧验证必须用“N 帧挂载、N+K 帧测量”的既有模式（horse/jeep/raft 同款），或把速度赋值等可同步读取的量做成单帧断言。
- 迁移收益：glb 蒙皮网格替换了每个角色几十上百个程序化零件节点，野图节点数从约 7700 降到约 6900、战场图从 5294 降到 4164，动画质量与帧率同时受益。

### 5.37 第三十二轮：启动变慢的根因与高度网格烘焙

- 症状：用户感觉启动越来越慢。打点分段计时（[boot_t]/[props_t] 常驻打印）后发现：13 个 glb 角色全部加载只花 85ms，而 16 万草叶的拒绝采样占 7.7s——每次尝试要 5 次 fBm 解析求值（get_height + get_normal 的 4 次差分），最多 128 万次尝试。
- 修法：terrain 启动时一次性烘焙 193² 高度网格与草甸噪声网格，之后 get_height_baked/get_normal_baked/get_patch_baked 全部 O(1) 双线性查表；草地从拒绝采样改为“预筛合格网格→直接抽样”（筛选 5 万格一次，抽样零拒绝）。grass 7.7s→0.24s，地形+植被段 9s→1.5s，整靴约 2.8s。
- 水位高度图烘焙复用同一网格，不重复求值；双线性值与地形网格一致（同源网格），视觉无差异。
- 教训：性能问题先分段计时再动手，根因常在反直觉处（新角色加载 vs 老植被采样）；大数量拒绝采样要算“尝试次数×单次成本”，而不是只看成功次数。

### 5.38 第三十三轮：启动再提速（复用烘焙网格 + 高度图碰撞 + 贴图磁盘缓存）

- 症状：5.37 优化后用户又感觉“启动越来越慢”。临时打点（[terr_t]/[wild_t]）定位：地形网格顶点循环 790ms（每顶点 5 次解析高度求值：高度 1 次 + 法线差分 4 次）+ 顶点色道路距离每点遍历全部路段；trimesh 碰撞烹饪 156ms；四张程序化贴图约 110ms（GDScript 逐像素光栅化）；props 树聚类偏移路径误用解析 get_height。
- 修法：
  1. _ready 先 bake_height_grid 再 _build；网格顶点的高度/法线/patch 直接读烘焙网格（顶点即格点，无双线性误差），法线用格点中心差分。vertloop 790→47ms。
  2. 48² 道路邻近掩码：只在可能贴路的格子做精确线段距离。
  3. 碰撞从 create_trimesh_shape 换成 HeightMapShape3D（map_data 直接复用 _height_grid，body.scale=(step,1,step)）：烹饪 156→0ms，运行时射线查询同样受益。Godot Physics 支持非均匀缩放的高度图（movetest/wildtest 全绿实证）。
  4. TexGen 贴图走 user://texcache PNG 磁盘缓存（TEX_CACHE_VERSION 控制失效，改生成算法时递增）：forest 146→37ms。
  5. props 树聚类偏移 get_height→get_height_baked。
- 结果：wild 图游戏内生成 1771→466ms；headless 整进程 3.35→2.05s；窗口模式到可玩约 4.8→1.9s（--quit-after 的耗时含 vsync 帧时间，勿当启动耗时）。
- 教训：5.37 只优化了“调用方”（草地采样），没动“被调方”（地形自身的网格生成仍走解析路径）；解析高度是公共热点，所有高频调用都应走烘焙网格。纯种子函数的程序化资产上磁盘缓存零风险，版本号常量防失效。

### 5.39 第三十四轮：近战判定、敌人前摇与模型层次

- 症状：普通敌人看似有血量，实战却经常一碰就消失并重复掉落；一剑偶尔扣双倍血。证据是多个 `take_damage` 把 `alive=false` 放在生命判断里，却把计击杀、掉落和 `queue_free` 错放到了判断外；玩家近战又先射线命中、再用扇形组遍历命中同一个 CharacterBody3D。
- 修复：所有受影响敌人以 `hp > 0: return` 明确分开“受伤”和“死亡”状态；奖励只在死亡路径执行，清理不依赖击杀者类型；近战用实例 ID 集合去重。wildtest 固定输出 `melee monster_hp 60->34`（基础剑只扣 26）和 `combat nonlethal=true`（轻伤不计击杀、不掉落）。
- 战斗节奏：山地小怪、莫布林和蜥蜴都加入可读前摇环；蜥蜴蓄力结束时锁定冲刺方向，不再在突进途中追踪拐弯。玩家剑击会打断前摇并按体型施加硬直/击退，第三段硬直更长。
- 第一人称反馈：剑模拆成剑脊、双刃、嵌片、护手、缠柄、手掌和袖口；挥击按剑根/剑尖逐帧生成三角带残影，轻击蓝、终结击金。挥空、命中和敌人蓄力使用三种独立程序化 WAV，命中继续保留真实时间顿帧。
- Blender 模型：莫布林增加长口鼻、眉弓、瞳孔、鬃冠、獠牙、腰甲、护肩、护腕、鞋和带刺棒，并补 `die` 倒地剪辑；蜥蜴增加分层长吻、瞳孔、腹甲、腰巾、指/趾爪、骨矛与 `prepare` 蓄力剪辑。GLB 仍只由对应 Python 生成脚本产出。
- 程序化音效的随机序列也属于兼容边界：新 `noise_burst` 如果插到旧生成流程中间，会改变后续音乐与环境音的固定随机序列。新增音效必须放到旧流程末尾，避免无关 WAV 全部产生二进制差异。

## 6. 音频生命周期

- 背景音乐和环境音由脚本生成的 WAV 提供，运行时设置循环区间。
- 失焦暂停必须显式设置 `stream_paused`。
- 场景退出或重载时，先停止 AudioStreamPlayer，再把 `stream` 设为 null，并清理缓存引用。
- 音频继续播放不等于 SceneTree 还在处理；诊断时要结合帧心跳和焦点日志。

## 8. 卡死问题的推荐排障顺序

1. 先记录画面、AI、HUD、音乐、音效、鼠标指针中哪些仍在变化。
2. 检查 Godot 日志最后一条游戏心跳和 `[focus]` 日志，不要只看系统“应用无响应”。
3. 用固定种子和 `--sim` 排除脚本死循环、对象增长和比赛阶段相关问题。
4. 用窗口化长时测试覆盖 GPU、shader、透明材质和真实音频路径。
5. 主动切换应用、释放鼠标、进入载具、投掷烟雾、死亡和重开，检查状态切换是否对称。
6. 如果出现 macOS 崩溃报告，先核对 PID、时间、父进程和启动参数；诊断工具自身的崩溃不能混作游戏崩溃。
7. 找到根因后增加专用命令行自检，避免只依赖人工复现。

## 9. 版本库边界

- 提交源脚本、程序化生成脚本、必要的 WAV、Godot `.import` 和 `.uid` 元数据。
- 不提交 `.godot/`、`tools/Godot.app`、`tools/godot.zip`、系统日志和 `/tmp` 截图。
- 提交前运行 `git diff --check`，确认没有空白错误；提交后确认工作区干净。

## 10. 维护本文

以后每个值得保留的问题至少记录：

- 用户看见的症状；
- 用来排除错误方向的证据；
